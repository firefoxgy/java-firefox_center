# CCWB 到 Firefox 全量命名迁移设计

## 目标

将项目自有品牌标识从 `ccwb` 全量迁移为 `firefox`，覆盖源码、构建坐标、模块、服务、配置、数据库标识、目录、文件、前端和文档，同时保持现有功能及模块关系不变。

## 范围

迁移以下项目自有标识：

- `ccwb` → `firefox`
- `CCWB` → `FIREFOX`
- `Ccwb` → `Firefox`
- Java 命名空间 `com.ccwb` → `com.firefox`
- Maven `groupId`、`artifactId`、模块名和项目内部依赖
- Spring 应用名、Nacos 服务名、配置键前缀和项目自有环境变量名
- 项目自有数据库名、表名或 SQL 中的 CCWB 品牌标识
- Java、资源、前端和文档中的引用
- 名称包含 CCWB 标识的项目目录、模块目录及文件
- 项目根目录 `java-ccwb_center` → `java-firefox_center`

不重写 `.git` 历史，不修改 `target`、`logs`、IDE 缓存、运行日志等生成内容。生成内容由后续构建或运行重新产生。

## 边界规则

只有项目自有命名被迁移。第三方库、协议、外部产品以及不属于本项目控制的外部接口名称不因字符串相似而改名。

对于数据库、Nacos、Redis、外部调用方等部署环境中的名称，源码和配置模板会迁移到 Firefox 命名；实际外部资源需要在部署时同步创建或迁移，否则新代码不能直接连接旧名称资源。

现有未提交修改必须保留，包括网关过滤器和父 POM 中的用户改动。批量处理不得用版本回退覆盖工作区。

## 实施方式

采用结构化批量迁移：

1. 建立受控的大小写映射，先修改文件内容，再迁移文件和目录名称。
2. 文本修改仅处理可识别的源码、配置、脚本、SQL、前端和文档文件，跳过二进制文件与生成目录。
3. 包路径与 Java `package`、`import` 同步迁移，确保目录和声明一致。
4. Maven 模块路径、父子关系、依赖坐标和源码模块名同步迁移。
5. Spring/Nacos 服务发现名称及网关 `lb://` 目标同步迁移，避免新旧服务名混用。
6. 配置前缀、占位符和绑定类同步迁移，避免配置无法绑定。
7. 最后迁移仓库根目录，后续验证均在新路径执行。

为降低目录重命名冲突，目录按照由深到浅的顺序处理；文件内容替换后执行旧标识残留扫描，并人工审查剩余命中。

## 验证

迁移完成必须满足：

- 排除明确的生成目录和 Git 历史后，不再存在项目自有 `ccwb`、`CCWB` 或 `Ccwb` 标识。
- 所有 Java 源文件的包声明与物理路径匹配。
- 所有 Maven `<module>` 路径实际存在，项目内部依赖坐标能够解析。
- 网关路由服务名与各服务的 `spring.application.name` 一致。
- 前端不存在指向旧服务或旧路径的项目自有引用。
- 从后端父工程执行 Maven 编译验证；若私服或外部依赖不可用，需区分命名迁移错误与环境依赖错误。
- 执行前端依赖范围内可用的静态检查或构建；若依赖未安装，则至少完成引用和配置一致性检查。
- 最终核对 Git diff，确认用户原有修改仍在且没有生成文件混入。

## 风险与回滚

这是破坏兼容性的命名迁移。外部调用方、部署脚本、Nacos 配置、数据库资源、镜像仓库和监控系统必须与代码同步切换。代码层面通过 Git 变更记录回滚；外部资源迁移需要部署方另行准备可逆迁移步骤。

本次任务只迁移当前仓库内容，不直接修改仓库之外的运行环境或外部系统。
